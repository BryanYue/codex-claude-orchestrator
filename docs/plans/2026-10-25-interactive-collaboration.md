# Interactive collaboration delivery plan

Status: authorized for implementation, independent review and release after acceptance. Source baseline: `f89bdcd` (1.0.1); delivery branch: `codex/collaboration-interaction-1-1`. Target: 1.1.0. This plan is the implementation contract; earlier research proposals are background where they differ.

Scope clarification, 2026-10-26: this release optimizes local multi-CLI coordination. Acceptance focuses on messages and answers, pending-question ownership, concurrency, cancellation/deadlines, recovery, task/round titles, workbench requests and two Codex instances. Keep native tools and auto permissions, and retain the existing copy/patch workflow. Ordinary read-only behavior and stopping run-owned processes are checked as part of task correctness. General security audits, credential/policy hardening and host-permission redesign are outside this release. This clarification takes precedence over broader interpretations of the checks below.

## User-visible behavior

- Codex and Claude exchange questions, disputes, answers and task updates while a task is running. Ordinary issues do not stop useful work. Codex resolves decisions inside the existing authorization; only unresolved core requirements, acceptance conflicts or other decisions outside that authorization go to the user. Planning follows task complexity; there is no mandatory start approval.
- One workbench belongs to a stable Codex namespace and root chat. Tasks and rounds are selected inside that page. Queued opens count as requested; reconnecting, compaction or a new round does not automatically request another page. Explicit reopening remains possible.
- Tasks have short human-readable titles and optional round descriptions, independent of the verbatim user-message archive. Continuations keep the task title unless explicitly renamed; round descriptions explain what changed. The workbench displays project/context, task, round and state separately. Existing records remain readable without rewriting their original messages or titles on disk.
- Claude uses its native tool set and native `auto` permission mode. The plugin does not maintain model tool allow/deny lists, force a search-tool preference or remove capabilities by analysis/implementation kind. It does not replace user/organization settings. Source/workspace isolation and task authorization remain distinct from which tools the model can see.
- Go, an Agent SDK package migration, new authentication/billing arrangements and a general distributed platform are out of this release.

## Architecture and invariants

Retain the local CLI and an independent worker for each run. A disconnected MCP frontend must not destroy a live worker. The worker owns the CLI streams, turn and process family. A parent turn result is not necessarily the end of an interactive run. Keep raw evidence, frozen inputs, disposable-copy patch/carry semantics, original-source protection and independent Codex decisions.

Use a versioned transactional control store for namespace/chat ownership, commands and receipts, interactions, task revisions and workbench opening reservations. Large logs and artifacts remain files. Existing v1 records are available through a read-only adapter; do not migrate active v1 execution into a second owner or double-write live state. New interactive runs have one explicit owner and attempt. SQLite must use a maintained version containing the relevant WAL-reset fix; otherwise use a verified supported journal/dependency arrangement, never claim this check has passed merely because import works.

Bind namespace, chat, task, run, attempt, session and turn separately. Resolve trusted launcher/request metadata where available; verify actual MCP availability of the observed Codex thread environment rather than assuming all surfaces inherit it. An explicit persisted chat binding is an acceptable fallback. If no stable binding can be recovered, provide a link rather than guessing from cwd/title/latest run. Missing automatic tab guarantees must be reported honestly.

Commands carry a unique id, payload hash, target, owner and expected revision. Same id/same payload is idempotent; same id/different payload conflicts. State, event and receipt updates commit atomically. An answer is tied to its pending interaction and effective revision. Record coordinator answers as coordinator, and user words verbatim as human. Transport write, runtime echo and semantic use are separate evidence states; never label echo as model understanding.

Only serious unresolved issues block dependent actions. Noncritical notes return immediately. Waiting needs an execution-side guarantee: it is not enough to prompt Claude to stop. If dependency scope cannot be established, pause the affected run's mutation phase while independent runs continue. Account for already-running Bash, workflows and subagents. An interrupt request is not proof of process-family stopping. Lease expiry is not proof of death; an uncertain worker is reconciled before a replacement can write. Controls/replies must not wait for a new-job execution slot.

Native tools remain available in analysis too; a requested read-only operation is enforced by the task and an OS write boundary as applicable, not a hidden Read/Glob/Grep-only list. Do not implement automatic global credential, hook or organization-policy changes. Native auto permission support and interaction with the question/control host are acceptance gates; do not silently fall back to dontAsk or a reduced tool set.

Before removing the old readonly tool list, implement its OS write protection for the source cwd, Git metadata and plugin/runtime state. On a host without a working supported boundary, reject the protected operation with a clear capability error rather than silently running it with instruction-only protection. Copy execution retains its existing original-source boundary. Do not use strict empty MCP configuration or disabled slash commands merely to recreate a hidden tool restriction; preserve user/organization configuration within the task's authorization.

CLI 2.1.310 probes verified `--tools default`, `--permission-mode auto`, `--input-format stream-json`, `--replay-user-messages` and `--permission-prompt-tool stdio`. The last option is not independently listed in help, so validate actual initialization: nonempty native tools, `AskUserQuestion` and `permissionMode=auto`. Fail clearly when unavailable. Handle each control request with a typed response or durable pending interaction; permission escalation is resolved against task authorization by Codex, not blindly allowed or denied as a tool policy. Parse repeated init/result events as turns of one CLI process. Interrupt may produce an error result and does not imply successful task completion or family stopping.

The serious-question execution guarantee is an implementation gate. A native blocking question stops the asking agent but does not prove background Bash/Workflow/subagents stopped. Implement and test a bounded process-family hold/recovery or safely stop and resume the affected execution with persisted interaction/session evidence. Do not remove this guarantee because a frontend Bash interrupt succeeded. Nonblocking notes need a typed, documented marker and immediate acknowledgment; their scope must not be inferred from incidental human wording alone.

## Minimal public surface

Extend packets with task `title`, optional `round_title`, stable context binding and an interactive mode/lifecycle contract. Existing packets and historical records retain documented behavior. Add typed answer/message control with durable receipts; answer, update, interrupt and cancel retain distinct semantics. Keep ordinary start/status/result/decide/cleanup coherent with the new lifecycle. Query/cancel/decide/reply must validate owner/context, including two Codex instances with identical local task names.

`wait` returns actionable interactions, requested visible changes, terminal changes or a bounded timeout. Hidden provider/tool activity must not create empty immediate wakeups. Multi-run waits, if added, return the first relevant change with independent cursors. Preserve raw events and complete artifact access.

Opening reservations are keyed by namespace/root chat/surface, not connection/run. Persist attempted before asking the host to open; queued is final for the automatic request. Unknown outcomes do not cause blind retries. A stable page identity does not require an eternal token or fixed machine-wide port. Without host idempotency/tab APIs, guarantee the plugin's request policy rather than claiming actual visible-tab exactly-once.

Titles are display metadata, never authority or routing keys. Prefer a supplied concise title and round description. Without them, derive a useful bounded fallback from coordinator task context or local task identity rather than always copying the first user sentence. Document how Codex supplies meaningful titles. Escape untrusted display content, keep full original words in the brief/details, and show identifiers as secondary metadata.

Concrete title precedence is explicit title, previous lineage title, then task_id; use single-line limits of 60 characters for title and 80 for round_title. The display can show title, round number and round_title together. Workbench responses include a durable `workbench.open` instruction (or equivalently explicit reservation result); only a newly reserved automatic request permits Codex to call open_in_codex. Neither a changed URL nor an absent chat identity authorizes another automatic request. Unknown identity stays link-only. Avoid pinning an eternal token/port to simulate host tab identity.

Keep the transactional store limited to the actual commands, interactions and opening/ownership records needed here. No job scheduler, multi-run wait or general lease service is required. One lock over several independently appended files is not a crash-atomic transaction; retain payload-conflict/revision checks and atomic receipts. A supported SQLite rollback journal arrangement is acceptable and need not introduce a new database package solely for WAL.

## Work packages

1. Capability probes and baseline: validate native auto/tool availability, current CLI duplex input and question channel in an isolated fixture, cancellation/interrupt behavior, and actual context metadata. Preserve raw evidence and distinguish test-double, real CLI and host UI results.
2. State/identity and display: implement transactional command/interaction/opening records, stable chat binding, readable title/round fields and task grouping. Keep old history readable. Cover namespace collisions and concurrent decisions.
3. Duplex execution: keep input open, route durable updates/answers, expose nonblocking notes and serious questions, implement waiting/resume/interrupt/cancel with correct turn/result ownership. Preserve copy, patch/carry and cleanup invariants.
4. MCP/UX and documentation: effective wait responses, workbench attention/current-round UI, single-opening request policy, native auto tools, updated Chinese/English docs and skill instructions. Do not expose low-level bookkeeping unnecessarily in normal product flows.
5. Integration acceptance: focused tests plus all required plugin/bridge/distribution/quality checks; real CLI fixtures for a mid-run answer, update, continuation, native tools and stopping. Two context identities in parallel, lost acknowledgments, stale/repeated answers, revision/cancel races, worker/frontend restart and original-source protection must have meaningful controls. Reuse known successful evidence and retain failed evidence.
6. Review and remediation: Claude implements in its independent copy; Codex reviews actual diff/artifacts and independently validates. After integration, Claude must run the shipped native `codex-analyze` Workflow for a full review with multiple dimensions and independent verification, and wait for actual Workflow completion. Codex commissions separate adversarial reviews of state/concurrency/recovery, execution/authorization/isolation, and UX/protocol/compatibility. Resolve confirmed findings, preserve independent counterexamples, and re-check affected paths. No self-reported completion or majority vote counts as acceptance.
7. Release: update consistent 1.1.0 manifests/docs/lock identity, commit only approved public source/docs, build twice from the same clean commit, verify hashes/manifests/archive, publish through the repository release mechanism, then download and reverify assets. Private research/history evidence stays local. Existing releases/tags remain immutable. Do not replace the running installed plugin or restart other chats as an implicit part of publishing; use isolated candidate connections for acceptance.

## Ownership, stops and rollback

Claude is the sole product-code writer while its implementation run is active. Codex owns private progress, verification and final integration/release; read-only reviewers do not edit source. Transfer writing only after the old writer is confirmed stopped. The canonical progress record remains the existing collaboration task record; public plan/check summaries contain no local account histories or secrets. Codex runs OS-boundary and real copy/readonly CLI acceptance outside the delegated copy sandbox; nested-sandbox skips in Claude's tests do not count as passes. Before every public commit, inspect the exact staged paths and content and exclude private research/history evidence.

Stop dependent work and ask the user only for a genuinely unresolved change to core requirements/acceptance, authorization or external publication scope, or an obstacle that cannot be resolved inside this contract. Routine implementation choices, test repairs that preserve behavior, bounded experiments and review corrections proceed autonomously. Environment failures are not product failures; preserve evidence before changing the hypothesis or test environment.

Rollback new runs by selecting the previous execution adapter only after they are safely stopped; retain their records. V1 active tasks stay with their original owner. Never claim lossless rollback by exporting v2 state into the old registry. Release rollback uses a new corrective release or the prior immutable tag, not overwriting published assets.
